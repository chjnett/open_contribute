# 메시지 템플릿 & 톤 가이드

빈칸 채우기용 템플릿이 아닙니다 — 모든 메시지는 그 레포, 이슈, 사용자의 실제 배경에 맞춰 매번 새로 써야 합니다. 아래는 그대로 복붙할 대본이 아니라 구조를 위한 참고입니다.

## 1. 이슈 클레임 코멘트

**목적:** 다른 사람이 중복 작업하지 않도록 의사를 표시하고, 메인테이너가 별다른 왕복 없이 "좋아요"라고 답할 수 있을 만큼의 정보를 주는 것.

**구조 (2~4문장):**
1. 이 이슈를 작업하고 싶다고 밝히기
2. 이슈가 조금이라도 모호하다면 계획한 접근 방식을 한 문장으로 (사소한 이슈라면 생략 — 괜히 늘어질 뿐)
3. (선택) 정말 불명확한 부분이 있다면 구체적인 질문 하나 (잘못 짐작해서 작업을 다시 하는 것보다 낫습니다)

**캐주얼 버전 예시 형태:**
> "제가 이거 작업해볼게요 — [한 구절로 된 접근 방식]으로 하려고 합니다. 시작하기 전에 방향이 맞는지 알려주세요."

**좀 더 상세한 버전 예시 형태:**
> "제가 맡을게요. 계획은: [구체적 단계 1~2개]입니다. 질문 하나 있는데 — [구체적으로 모호한 부분], 아니면 [합리적인 가정]으로 진행해도 될까요?"

**피할 것:**
- 오픈소스가 처음이라는 긴 자기소개 (메인테이너는 자서전이 필요 없습니다)
- 이슈를 읽었다는 근거 없이 막연하게 "고쳐볼게요"
- 이슈 본문이나 CONTRIBUTING.md에 이미 답이 있는 질문

## 2. Discord/Slack `#contributing` 아웃리치

**목적:** "환영합니다! good first issue 라벨 확인해보세요" (사용자가 이미 시도했던) 같은 답 말고, 구체적이고 실제로 쓸모 있는 답을 빠르게 받는 것.

**구조:**
1. 관련 배경 한 줄 — 언어/스택 정도, 전체 이력서 수준은 아님
2. 정확히 뭘 찾고 있는지: "작업할 거리"보다 "현재 열려있고 아무도 안 잡은 good-first-issue"가 훨씬 구체적입니다
3. 필요하다면: 라벨 붙은 이슈들을 확인했는데 이미 다 클레임돼 있었다는 언급 — 숙제를 해왔다는 신호가 되고, 메인테이너가 같은 목록을 다시 추천하는 수고를 덜어줍니다

**예시 형태:**
> "안녕하세요, 여기 첫 기여를 해보고 싶어서요. [스택] 다룰 줄 압니다. good-first-issue 라벨 확인했는데 상위 몇 개는 이미 PR이 걸려있더라고요. 지금 열려있는 것 중에 추천해주실 만한 게 있을까요, 아니면 손이 필요한 영역이 있을까요?"

**피할 것:**
- "안녕하세요 기여하고 싶은데 어떻게 하나요" 같은 맥락 없는 문구 — 바쁜 채널에서는 우선순위가 밀립니다
- 첫 메시지부터 풀 온보딩/멘토링 세션 요청 — 대부분의 메인테이너는 그럴 여유가 없습니다

## 3. Pull Request 설명

**목적:** 그 프로젝트의 최근 PR과 형식을 맞춰서 빠르게 리뷰받는 것.

**구조:**
1. 먼저 최근 머지된 PR 2~3개를 확인하세요 — 제목 형식(`[BUG] 짧은 설명` vs `fix: 짧은 설명`), 템플릿(`.github/PULL_REQUEST_TEMPLATE.md`) 사용 여부를 체크
2. 템플릿이 있으면 그걸 쓰세요 — 임의로 다른 구조를 만들지 마세요
3. 없다면: 무엇이 바뀌었는지, 왜 바뀌었는지, 어떻게 테스트했는지, 이슈로의 링크(`Closes #1234`)

**피할 것:**
- diff에서 이미 보이는 구현 세부사항을 과도하게 설명
- 비직관적인 선택을 한 이유를 설명하지 않고 넘어가기
- 사소한 변경이라도 "어떻게 테스트했는지" 섹션 생략 — 없으면 리뷰어가 어차피 물어봐서 리뷰 왕복만 늘어납니다

## 4. PR을 볼 사람에게 제대로 닿게 하기

이 섹션은 전부 **라우팅과 명확성**에 관한 것이지 압박이 아닙니다. PR이 멈추는 건 그 코드를 소유한 사람이 보고 거절해서가 아니라, 그 사람이 PR의 존재를 모르기 때문인 경우가 훨씬 많습니다.

### CODEOWNERS 라우팅 확인 — 단, "깨졌다"는 판단은 아주 신중하게

`.github/CODEOWNERS`에서 내가 건드린 코드의 소유 팀을 확인하세요. 대개는 "정상 라우팅됐고 할 일 없음"이 답이고, 그게 기대해야 할 결과입니다.

**리뷰어 목록만 보고 라우팅 공백이라고 단정하지 마세요.** 많은 조직이 팀 리뷰 요청을 그 팀 개인들로 치환하는데, `requested_reviewers`만 읽으면 잘못 라우팅된 것과 구분이 안 됩니다. 타임라인을 보세요:

```bash
gh api "repos/{owner}/{repo}/issues/{n}/timeline?per_page=100" \
  --jq '.[]|select(.event=="review_requested" or .event=="review_request_removed")
        | "\(.event): \(.requested_team.slug // .requested_reviewer.login)"'
```

실제 사례 — `grafana/grafana#130614`은 프론트엔드 개인 4명만 보이고 팀이 없어서 소유 스쿼드가 누락된 것처럼 보였습니다. 타임라인은 달랐습니다: CODEOWNERS로 `sharing-squad`가 자동 요청됐다가 제거되고 그 팀 멤버 4명으로 치환된 것이었습니다. 라우팅은 처음부터 정상이었고, 알릴 공백도 없었으며, 공백이라고 주장하는 코멘트를 올렸다면 그냥 틀린 말이 됐을 겁니다.

파일이 **정말로** 어느 규칙에도 매칭되지 않을 때만 — 잘린 검색 결과가 아니라 CODEOWNERS 항목을 직접 읽어서 확인한 뒤에 — 코멘트 하나가 의미 있습니다:

> "CODEOWNERS routes the {기능} paths to @{팀}, but `{파일}` isn't covered by a rule so this didn't reach them — flagging in case it belongs on their queue."

**이 실수가 어떻게 났는지도 남깁니다.** 첫 시도에서 `grep shortLinks CODEOWNERS | head -5`를 돌렸는데 매칭된 줄이 여섯 번째였고, 출력이 없다는 게 "미커버"가 돼버렸습니다. 공개적으로 할 사실 주장을 출력 제한이 대신 결정하게 두지 마세요 — `head`를 빼거나 매칭 수를 먼저 세세요.

### 이슈 스레드에 PR이 올라갔다고 알리기

이슈를 구독 중인 사람이 내 포크의 PR까지 자동으로 구독하지는 않습니다. 이슈에 짧은 코멘트 하나면 그 간극이 메워지고, 같은 버그를 겪는 사람이 수정본을 찾을 수 있습니다.

> "Opened #{pr} for this — {접근 방식 한 구절}."

### 커뮤니티 채널

`CONTRIBUTING.md`가 Slack/Discord/포럼을 링크하고 있다면(Grafana는 커뮤니티 Slack과 포럼을 링크합니다), PR이 한동안 리뷰 없이 방치된 **뒤에** 한 번 올리는 건 합리적입니다. 링크 + 한 문장 맥락 + 적절한 팀에게 닿았는지 질문. 한 번만, 맞는 채널에, `@here`/`@everyone`은 절대 금지.

## 5. 재촉은 딱 한 번

아무 반응이 없다면 후속 코멘트는 **한 번**이고, 새로운 정보를 담아야 합니다.

**먼저 기다리세요.** 큰 레포에서 1~2주 침묵은 무시가 아니라 정상입니다 — 외부 PR의 CI는 메인테이너 승인 대기로 잡히는 경우가 많아서, "체크가 안 돌고 있다"는 것도 방치의 증거가 아닙니다.

**읽을 가치가 있게 만드세요.** 뭔가 바뀌었거나 뭔가를 해결했을 때:

> "Rebased on main and CI is green. Happy to adjust the approach if the `bootData` route isn't what you'd prefer."

**그리고 멈추세요.** 몇 주 뒤 두 번째 재촉이 필요하다면 같은 스레드에 또 다는 대신 다른 창구(커뮤니티 Slack)를 쓰세요. 메인테이너는 대개 수백 개 대기열을 가진 자원봉사자이고, 침묵은 거절이 아니라 여력 부족인 경우가 많습니다.

## 6. 리뷰를 잃게 만드는 것들

압박으로 읽히고 확실히 역효과가 납니다:

- 여러 메인테이너를 한꺼번에 `@` 하거나, 그 영역과 무관한 사람을 `@` 하기
- 새 정보 없는 "Any update?" / "bump" / "please review"
- 며칠 만에, 혹은 반복해서 재촉하기
- 먼저 청하지 않은 메인테이너에게 DM 보내기
- 관심을 끌려고 무관한 이슈나 PR에 코멘트 달기
- 반응이 없다고 중복 이슈를 새로 만들기
- 메인테이너가 방향을 거절한 뒤에 논쟁을 다시 여는 것

확실히 효과 있는 건 지루한 것들입니다: PR을 작게 유지하고, 머지 가능한 상태로 유지하고, 리뷰 코멘트에 빠르게 답하고, 리뷰어가 20분 걸릴 일을 2분에 끝내게 만드는 것.
