# 메시지 템플릿 & 톤 가이드

빈칸 채우기용 템플릿이 아닙니다 — 모든 메시지는 그 레포, 이슈, 사용자의 실제 배경에 맞춰 매번 새로 써야 합니다. 아래는 그대로 복붙할 대본이 아니라 구조를 위한 참고입니다.

## 1. 이슈 클레임 코멘트

**목적:** 다른 사람이 중복 작업하지 않도록 의사를 표시하고, 메인테이너가 별다른 왕복 없이 "좋아요"라고 답할 수 있을 만큼의 정보를 주는 것.

**구조 (2~4문장):**
1. 이 이슈를 작업하고 싶다고 밝히기
2. 이슈가 조금이라도 모호하다면 계획한 접근 방식을 한 문장으로 (사소한 이슈라면 생략 — 괜히 늘어질 뿐)
3. (선택) 정말 불명확한 부분이 있다면 구체적인 질문 하나 (잘못 짐작해서 작업을 다시 하는 것보다 낫습니다)

**캐주얼 버전 예시 형태:**
> "제가 이거 작업해볼게요 — [한 구절로 된 접근 방식]으로 하려고 합니다. 시작하기 전에 방향이 맞는지 알려주세요."

**좀 더 상세한 버전 예시 형태:**
> "제가 맡을게요. 계획은: [구체적 단계 1~2개]입니다. 질문 하나 있는데 — [구체적으로 모호한 부분], 아니면 [합리적인 가정]으로 진행해도 될까요?"

**피할 것:**
- 오픈소스가 처음이라는 긴 자기소개 (메인테이너는 자서전이 필요 없습니다)
- 이슈를 읽었다는 근거 없이 막연하게 "고쳐볼게요"
- 이슈 본문이나 CONTRIBUTING.md에 이미 답이 있는 질문

## 2. Discord/Slack `#contributing` 아웃리치

**목적:** "환영합니다! good first issue 라벨 확인해보세요" (사용자가 이미 시도했던) 같은 답 말고, 구체적이고 실제로 쓸모 있는 답을 빠르게 받는 것.

**구조:**
1. 관련 배경 한 줄 — 언어/스택 정도, 전체 이력서 수준은 아님
2. 정확히 뭘 찾고 있는지: "작업할 거리"보다 "현재 열려있고 아무도 안 잡은 good-first-issue"가 훨씬 구체적입니다
3. 필요하다면: 라벨 붙은 이슈들을 확인했는데 이미 다 클레임돼 있었다는 언급 — 숙제를 해왔다는 신호가 되고, 메인테이너가 같은 목록을 다시 추천하는 수고를 덜어줍니다

**예시 형태:**
> "안녕하세요, 여기 첫 기여를 해보고 싶어서요. [스택] 다룰 줄 압니다. good-first-issue 라벨 확인했는데 상위 몇 개는 이미 PR이 걸려있더라고요. 지금 열려있는 것 중에 추천해주실 만한 게 있을까요, 아니면 손이 필요한 영역이 있을까요?"

**피할 것:**
- "안녕하세요 기여하고 싶은데 어떻게 하나요" 같은 맥락 없는 문구 — 바쁜 채널에서는 우선순위가 밀립니다
- 첫 메시지부터 풀 온보딩/멘토링 세션 요청 — 대부분의 메인테이너는 그럴 여유가 없습니다

## 3. Pull Request 설명

**목적:** 그 프로젝트의 최근 PR과 형식을 맞춰서 빠르게 리뷰받는 것.

**구조:**
1. 먼저 최근 머지된 PR 2~3개를 확인하세요 — 제목 형식(`[BUG] 짧은 설명` vs `fix: 짧은 설명`), 템플릿(`.github/PULL_REQUEST_TEMPLATE.md`) 사용 여부를 체크
2. 템플릿이 있으면 그걸 쓰세요 — 임의로 다른 구조를 만들지 마세요
3. 없다면: 무엇이 바뀌었는지, 왜 바뀌었는지, 어떻게 테스트했는지, 이슈로의 링크(`Closes #1234`)

**피할 것:**
- diff에서 이미 보이는 구현 세부사항을 과도하게 설명
- 비직관적인 선택을 한 이유를 설명하지 않고 넘어가기
- 사소한 변경이라도 "어떻게 테스트했는지" 섹션 생략 — 없으면 리뷰어가 어차피 물어봐서 리뷰 왕복만 늘어납니다
