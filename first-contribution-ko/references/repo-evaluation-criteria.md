# 레포 평가 기준

Phase 2에서 후보 레포를 채점하고 비교할 때 사용하세요. 아래 항목 중 하나만으로 탈락시키지 말고 종합적으로 판단하세요.

## 1. 이슈 양
오픈 이슈가 많을수록 대체로 기회가 많지만, 개수만 보지 말고 백로그의 성격을 함께 보세요.
- 오픈 이슈 50~2000개 정도에 적당한 종료율을 보이면 건강한 상태입니다.
- 오픈 이슈 10,000개 이상인데 최근 종료가 거의 없다면 방치된 레포일 가능성이 높습니다 — 기여해도 오래 리뷰가 안 될 수 있어요.
- 오픈 이슈가 10개 미만이면 메인테이너 팀이 매우 끈끈해서 진입이 어렵거나, 조용히 죽어가는 프로젝트일 수 있습니다.

종료율은 대략적으로라도 `open_issues_count`와 최근 이슈 종료 빈도를 비교해서 확인하세요(`state:closed`를 `closed:desc`로 정렬해서 몇 개 훑어보면 됩니다).

## 2. 최근 커밋/PR 활동
API의 `pushed_at`으로 마지막 푸시 시점을 알 수 있습니다. 함께 확인할 것:
- 외부(핵심 팀 아닌) 기여자의 PR이 최근에도 머지되고 있는지. 최근 머지된 PR 10~20개의 작성자를 확인해보세요.
- 자기 회사 직원 PR만 머지되는 프로젝트는 기술적으로는 "활발"하지만 실제로 외부 기여자에게 열려있지는 않습니다.

## 3. PR 머지 현실 (이슈 triage 전에 먼저 확인)

위 항목들은 외부 PR이 실제로는 하나도 안 들어가는 레포에서도 전부 건강해 보일 수 있습니다. 매일 푸시하고 분기당 수백 개 PR을 머지하면서도, 핵심 팀 바깥 사람의 PR은 거의 머지하지 않는 프로젝트가 있습니다. "활발한가"와 "외부에 열려있는가"는 다른 질문이고, 두 번째는 첫 번째에서 추론하지 말고 직접 측정해야 합니다.

**열린 PR 적체율** — 열린 PR 중 90일 이상 방치된 비율:

```bash
curl -s "https://api.github.com/search/issues?q=repo:{owner}/{repo}+type:pr+state:open"
curl -s "https://api.github.com/search/issues?q=repo:{owner}/{repo}+type:pr+state:open+created:<YYYY-MM-DD"  # 90일 전 날짜
```

**외부인 머지 비율** — 최근 90일간 머지된 PR 중 핵심 팀 바깥에서 온 비율:

```bash
curl -s "https://api.github.com/search/issues?q=repo:{owner}/{repo}+type:pr+is:merged+merged:>YYYY-MM-DD&per_page=100" \
  | jq -r '.items[].user.login' | sort | uniq -c | sort -rn
```

핵심 팀은 대개 이 목록에서 바로 드러납니다 — 상위를 차지하는 몇 개의 계정과 봇이 그들이고, 나머지가 외부인입니다.

| | 건강 | 경고 |
|---|---|---|
| 90일 이상 방치된 열린 PR | 약 30% 미만 | 약 50% 초과 |
| 외부인이 작성한 머지 PR | 25% 이상 | 약 10% 미만 |

둘 다 경고 구간이면 어떤 이슈를 고르든 첫 기여가 머지될 가능성이 낮습니다. **실제 수치를 사용자에게 보여주고 계속할지 직접 결정하게 하세요** — 그래도 그 프로젝트에 기여할 이유가 있는 사람도 있습니다(회사에서 쓰고 있거나, 그 코드베이스를 익히고 싶거나, 노출 목적이거나). 조용히 레포를 탈락시키지도 말고, 수치가 괜찮았던 것처럼 그냥 넘어가지도 마세요.

실제 사례 — `chroma-core/chroma`, 2026-08 확인. 표면 지표는 전부 좋았습니다: 스타 29k, 전날 푸시, 90일간 PR 238건 머지, 열린 `good first issue` 11건. 게이트 수치는 아니었습니다: 열린 PR 452건 중 275건(61%)이 90일 이상 방치, 머지 PR 중 외부인 작성은 약 9%, 그리고 good-first-issue에 올라온 PR 17건이 **전부 머지 실패** — 11건은 최장 8개월째 열린 채, 6건은 머지 없이 종료. 이슈 #2054에 남은 한 기여자의 마지막 말: "PR 머지가 너무 오래 걸려서 이 이슈에서 빠지겠다." 활동은 진짜였지만, 그 활동이 외부인에게까지 닿지 않았던 겁니다.

## 4. 일반 기여자 친화도
- Chroma의 `by-chroma`처럼 `by-<조직>` 형식의 라벨이 있다면, 메인테이너가 외부인이 접근하기 좋다고 직접 큐레이션한 이슈일 가능성이 높습니다 — 최근 활동과 함께 보면 좋은 신호입니다.
- CONTRIBUTING.md에 `#contributing` Discord/Slack 채널, 문서화된 스타일 가이드, "first-timers-only" 같은 프로그램이 있는지 확인하세요 — 모두 진입장벽이 낮다는 신호입니다.
- 한 회사가 커밋의 90% 이상을 차지한다고(클론 후 `git shortlog -sn`으로 확인하거나 최근 커밋 작성자를 훑어보면 됩니다) 무조건 나쁜 건 아니지만, 그 회사의 로드맵 방향으로 기여가 많이 좌우될 수 있다는 점은 알고 가야 합니다.

## 5. 기능 동결 여부
README와 최근 CHANGELOG/릴리즈 노트에서 "유지보수 모드(maintenance mode)", "기능 동결(feature freeze)", "더 이상 새 기능을 받지 않습니다", v0→v1 종료 공지 같은 문구가 있는지 확인하세요. 버그 수정만 받는 프로젝트는 첫 기여로 다룰 수 있는 범위가 훨씬 좁습니다 — 반드시 나쁜 건 아니지만, 사용자가 미리 알고 있어야 합니다.

## 6. 본인 관심사와의 적합도
가장 중요하면서도, 위 지표들에 과하게 최적화하다가 가장 놓치기 쉬운 요소입니다. 수치상으로는 조금 아쉬워도 본인이 실제로 쓰고 싶고 이해하고 싶은 레포가 더 좋은 기여로 이어집니다 — 코드를 진짜로 읽게 되니까요. 지표가 관심사를 압도하게 두지 말고, 최종 결정은 사용자가 내리도록 하나의 참고 정보로만 제시하세요.
